# SDK import-archive alignment bytes

The archive cursor in `interp/native/windows_imports.rs::providers` now accepts NUL or newline in the single required alignment byte following an odd-sized member. It still requires that byte to exist, reads exactly the declared payload size, and validates the following header at the resulting even address. Other padding bytes reject with their value and offset. Object metadata validation, exact CPU selection, provider identity/deduplication and DLL search/loading are unchanged from 6e149cac.

Microsoft's [PE/COFF archive specification](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#archive-member-headers) describes even-addressed member headers and newline `IMAGE_ARCHIVE_PAD`. The public Microsoft SDK artifact below instead uses NUL. LLVM's official [ArchiveMemberHeader::getNextChildLoc](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Object/Archive.cpp) computes the next header by even alignment; it does not require a particular padding value. The installed LLVM archive reader accepts this artifact. Our correction admits the two established padding encodings while preserving bounds and structural rejection; it does not scan for a later header or ignore a missing alignment byte.

The coordinator's admitted `runtimeobject-sdk-padding/admission.json` initially listed no files. We therefore fetched public NuGet `Microsoft.Windows.SDK.CPP.arm64` version `10.0.26100.6584`, verifying the already admitted package SHA256 `ac06922186fdd75e4ff1033a304ea629d7917bd0ca85e483762f8109584ccfc4`. Only `c/um/arm64/runtimeobject.lib` was extracted for metadata inspection: SHA256 `77c8bdaa5ea9e08e5ea4631ccefec562963a2248cfc8374881042cee199fe307`, 52150 bytes. Neither package nor archive is committed, and no SDK code or DLL was executed.

The exact 6e149cac parser rejects this artifact with `missing archive member padding`. Its first failing boundary is member index 2 (`//`): header at 10756, declared payload length 331, payload ends at 11147, NUL pad at 11147, next header at 11148, file EOF at 52150. All 156 archive members have aligned headers; 77 odd-member boundaries use NUL. The final member starts at 51990, has length 99, ends at 52149 and has its required NUL pad before EOF 52150. This is a real ARM64 SDK reproduction, **not the exact x64 Windows Kits 10.0.26100.0 CI file**.

Independent tests cover all 256 pad-byte values; accepted NUL and newline at interior and terminal boundaries; longnames padding; even payloads without padding; missing/extra padding; corrupt following headers; and truncated payload/header prefixes. The existing mixed-machine, wrong-CPU-only, malformed-member, duplicate/distinct-provider and tool-generated archive controls remain required. Initial test authoring used an even-sized payload for an odd-size control; that authoring failure is retained separately, and the corrected independent fixture reproduces the production rejection before the fix.

After correction the SDK metadata probe returns eight distinct API-set DLL providers. The existing loader's multiple-provider rejection is intentionally unchanged: this patch establishes correct archive parsing, not successful RuntimeObject loading. The coordinator needs the exact x64 archive/hash and actual Windows execution to qualify the CI repair, plus a separately reviewed general multi-provider symbol-resolution repair if that archive has the same requirement. No provider fallback, CPU coercion, module-specific mapping or malformed-metadata waiver was added.

Captures, package provenance, full per-member boundary metadata, RED/GREEN probes and scoped Cargo test/Clippy/rustfmt evidence are in the compiler T7 `mac-repairs-audit/runtimeobject-padding` directory. The previous mixed-machine patch and its receipts remain immutable. Uniform, module-lane code and all other compiler production files are untouched.
