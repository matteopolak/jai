# Per-symbol Windows import-library selection

Windows import libraries may describe several DLLs. The interpreter previously cached one DLL handle per logical library and rejected any archive with multiple providers before the requested foreign symbol reached lookup. The public ARM64 SDK `runtimeobject.lib` is an independent positive counterexample: it contains eight API-set providers, with different functions assigned to different providers.

The cached Windows library now retains validated short-import records and loaded provider handles. Lookup selects the exact declared public symbol and compatible CPU record, then resolves its actual export in that record's provider. Distinct symbols in distinct DLLs are supported. Duplicate records agree only when both case-insensitive provider identity and exact export target agree; conflicting records for the same public symbol remain an ambiguity error. Symbols and named exports remain case-sensitive. No match, a wrong-CPU-only symbol, or an unavailable selected export produces a diagnostic rather than a search through other DLLs or interpreter fallbacks.

The decoder retains the [PE/COFF import name type](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#import-name-type): ordinal (0), identical name (1), remove one leading decoration character (2), remove that character and truncate the suffix at the first `@` (3), or the separately encoded export-as name (4). It validates the complete declared payload, including the third string for export-as, before CPU or symbol filtering. Named lookup uses the resulting export bytes; ordinal lookup uses the documented low-word encoding for [GetProcAddress](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getprocaddress). Export-as behavior is also documented by LLVM's official [COFFImportFile implementation](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Object/COFFImportFile.cpp). Public linkage names are not guessed from export names or synthetic `__imp_` names, and ARM64EC records are never treated as ARM64.

Required-library opening still loads all compatible declared providers, preserving startup/constructor effects even before a foreign lookup. The selected archive remains authoritative: a provider load failure does not fall through to a lower-priority archive or guessed DLL. DLL search directories, source/configured/SDK precedence, ordinary DLL resolution and non-Windows loading are unchanged. Windows optional-library cache opening now preserves loader errors as well, preventing a rejected archive from becoming a libraryless lookup. A cached failed open continues to reject. `foreign_addr` propagates structured lookup diagnostics.

Long-COFF descriptor-only archives retain their existing single-provider behavior. Multi-provider long-COFF symbol/relocation association remains unsupported and explicitly diagnosed; it is not inferred from strings or an archive-wide first provider. This checkpoint does not claim general long-COFF multi-provider routing, synthetic IAT storage, new calling conventions, or successful Windows execution.

Owned production scope: `windows_imports.rs` record decoding/archive validation/selection; `windows.rs` logical library open/lookup; `native.rs` private Windows library representation and checked lookup; and the Windows cache-open/lookup section of `Interp::foreign_addr`. The cache remains keyed by logical library ID and foreign addresses remain keyed by foreign declaration. The old lossy Windows open/lookup convenience wrappers are needed only by existing unit tests and are compiled in test builds; production uses the checked interfaces. No parser, module-lane, stdlib, Extensions or ABI-call code changes.

Independent regressions cover disjoint-symbol multi-DLL selection, same-symbol ambiguity, conflicting export-as targets in one DLL, unknown/case-mismatched symbols, all name types, ordinal versus hint behavior, malformed alias payloads, exact CPU filtering and wrong-CPU-only symbols. All preceding padding, malformed/wrong-CPU archive, real LLVM/GNU metadata, single-provider and candidate-precedence controls remain. LLVM-generated x64/ARM64 fixtures independently verify the public symbol/export mapping; the GNU single-provider fixture remains a descriptor-only compatibility control.

The already admitted public Microsoft ARM64 SDK archive SHA256 `77c8bdaa5ea9e08e5ea4631ccefec562963a2248cfc8374881042cee199fe307` verifies all 64 compatible short imports across eight providers. `RoInitialize`/`RoUninitialize` select the core WinRT provider; `RoOriginateError` selects its error provider; `WindowsCreateString` selects its string provider. The separate ARM64EC `#RoInitialize` export-as record resolves to the named export `RoInitialize` only when selecting ARM64EC metadata. It is rejected when requesting ARM64. These are metadata checks, not SDK function execution.

Evidence and the exact NEW patch/manifest/source guards live under the compiler T7 `mac-repairs-audit/per-symbol-imports` directory. Windows x64 and ARM64 strict Clippy/source checks and host metadata execution are separately labeled. No SDK binary is committed and no SDK DLL is executed. The exact failing x64 CI archive and actual native Windows runtime qualification remain coordinator dependencies; no D3DCompiler/WebGPU runtime pass is claimed. The sealed 6e149cac and a8e9a92c patches remain unchanged.
