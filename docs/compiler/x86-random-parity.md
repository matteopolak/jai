# Random-instruction parity flags

The shared assembly lowering represented PF as a lazily evaluated result byte. Assigning byte zero to clear PF instead set it: zero has even parity. RDRAND/RDSEED therefore exposed PF=1, producing flags 16 or 17 depending on CF, in both interpreted and native code. The lowering now explicitly encodes the cleared PF bit through `parity_byte_for_bit`; the existing byte representation and other scalar/SIMD flag producers remain unchanged.

Intel's [instruction reference](https://cdrdv2-public.intel.com/782151/253667-sdm-vol-2b.pdf) requires OF/SF/ZF/AF/PF to clear for these instructions. The hardware sample, destination width, carry result, real CPUID checks and unavailable-instruction diagnostics are unchanged. No synthetic random value or success bit is introduced. The CI native driver's status 13 denotes a RDRAND check failure; its printed RDTSCP=0 is independently capability-guarded and does not itself explain that status.

An independent LLVM source oracle exposes PF alone while retaining the architectural sample. Restoring the old assignment in an isolated T7 build produces an optimized `ret i8 1` and a real failing assertion; the correction produces `ret i8 0`, while `asm sideeffect` remains. The pre-optimization `emit_ir` output is explicitly optimized with official LLVM `opt` before this assertion. The initial assumption that `emit_ir` was already optimized, and an initial broader flag-representation attempt, are retained as failed preparation receipts; neither is claimed as verified functionality.

Portable interpreter controls exhaust all 256 low-byte parities, high-bit independence, rotation preservation, explicit POPCNT flag clears and masked dynamic shift counts. The original architecture/operand/unsupported-cache/cycle-counter controls remain required. The C driver retains its assertions/statuses and now identifies width/flags in an arithmetic-flag failure.

Verification on this Mac ARM64 host: all seven ARM-host controls pass; the complete x86 interpreter controls pass through actual OS x86 translation (seven tests); the existing native opcode/architecture test passes across four object targets at O0/O2 and executes its Mac x86 C driver at both levels. Actual CPUID reports TSC=1, RDTSCP=1, RDRAND=0, RDSEED=0. Thus timestamp/fence/prefetch execution and unavailable-random diagnostics are verified here; real random-instruction execution on the affected Intel CI host remains required. The source oracle establishes the cleared-flag dataflow without pretending to execute unavailable hardware.
