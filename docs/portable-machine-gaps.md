# Machine_X64 compiler integration gaps

## Current implemented CPU-query batch

The NEW compiler handoff documents real CPUID leaf/subleaf input and four results.
After rebuilding from its authorized Rust sources, this worker implements
canonical x86_Vendor/x86_Feature_Leaf/x86_Feature_Flag/Cpu_X86, Prefetch_Hint and
Machine_Options_X86 records, plus get_cpu_info/check_feature/enable_feature/
disable_feature. The facade loads independently grouped private declarations;
no prefixed type aliases or private helper exports are introduced. Two hundred
reviewed feature values are explicit and generated by responsibility group, then
alphabetically within that group. Aggregate layouts remain exact.

get_cpu_info reads real vendor bytes and eleven native feature registers. It
guards standard/extended maximum leaves and structured subleaf availability;
unavailable leaves remain zero because the hardware does not expose them.
Unknown vendor text maps to the reviewed UNKNOWN enum. Feature bits are raw
architectural flags, not a guarantee that the OS has enabled every advertised
instruction. No XCR0-based dispatch policy is invented; fine reference gating
needs review. Out-of-array feature indexes assert as an independent safety rule.

An independent C program includes the official SDK cpuid.h and writes vendor plus
eleven words. Source-built native x64 O0/O2 Jai output matches all twelve words.
All352 bit positions exercise enable/check/disable, idempotence and independent
bits, with canonical reflected names and private-helper visibility assertions.
macOS/Linux/Windows x64 fixture bodies type-check. Actual native execution is
macOS x64 translation on this ARM64 host; it describes the translated environment,
not the physical ARM CPU. The original vendor assertion is promoted unchanged
to machine-x64/cpuid-vendor.jai and remains required in the focused native runner.

Source-built x64 jailint strictly checks the module and original fixtures. Its
compile-time fixture executes real CPUID and all352 mask operations through the
x64 interpreter, comparing baseline registers with direct original asm queries.
This is compile-time interpreter evidence; full native C comparison executes in
the separate native fixture. The ARM64 interpreter correctly diagnoses CPUID
execution as unsupported. The initial attempt to run the file-reading native
fixture inside jailint's SandboxHost aborted; that failed log is retained, and
no linter file-operation support is claimed. Native assertions remain intact.

Generation normalizes with source-built jaifmt and --check; repeated generation
is byte-identical. All313 owned files pass formatting. Focused x64 strict lint
passes; whole owned strict lint still fails on separately recorded semantic and
fixture-configuration gaps. New general field-array type and forward-enum
reproducers fail ordinary compiler checking as well as interpreter setup; these
are genuine compiler gaps, not solely eager-lint quirks.

### Exact remaining public API inventory

- get_machine_options_x86: implemented with the exact generic #modify signature.
  Reviewed Compiler.Build_Options supplies machine_options:[128]u8, and the
  reviewed44-byte Machine_Options_X86 overlays that caller-owned storage. A real
  struct constraint, byte-array/extent checks and reflected-alignment check
  reject unsupported storage. Interpreter/native O0/O2 tests use actual reviewed
  Build_Options, check pointer identity and two-way edits, and preserve bytes44..127.
  There is no allocation, snapshot, new field or separate feature storage. The
  returned pointer lives only while the caller's build-options value remains live.
- prefetch, rdtsc, rdtscp, rdseed, rdrand, mfence, lfence, sfence, pause: missing.
  The current compiler still makes fence mnemonics no-ops, random instructions
  synthetic and RDTSCP processor ID zero. Real architecture semantics or explicit
  diagnostics must be provided before those exports are counted complete.
- Windows/Linux native CPU-query execution remains a platform gate. No target
  checking is counted as native execution or full module completeness.

## Original failure evidence (CPUID now resolved)

The reviewed module is x64-only and promises architectural CPU/instruction
operations, without a non-x64 fallback. No zero-feature CPU record is supplied as
a completed implementation.

At the original probe checkpoint, own compiler lowered Op::Cpuid by writing literal zero into all
four operands in crates/jaic/src/sema/asm.rs. The original standalone
tests/portable-stdlib/pending/cpuid-vendor.jai queries leaf0 and asserts actual
nonempty vendor bytes. It fails in both interpreter and a source-built native
x64 executable, with the same specific assertion. Failed logs are retained at
target/cpuid-vendor-failure.log and target/cpuid-vendor-native-failure.log.

An independently authored C counterpart includes the official native C SDK
cpuid.h and actually executes the instruction. Compiled with clang -arch x86_64
-std=c11 -O2 -Wall -Wextra -Werror, it returns a real nonempty vendor/max leaf
(this run: GenuineIntel,13). No header body is copied or Jai implementation used.
The native Jai command selects x86_64-apple-darwin/x64 and disables crash-handler
installation for this focused assertion probe; its assertion remains active.
Existing full crash-handler tests remain enabled and passing separately.

Required compiler-owner fix: represent the CPU query with real leaf/subleaf input
and four results, lower native target execution to actual architectural CPUID,
and supply truthful interpreter behavior or an explicit unsupported-target
diagnostic. Do not recognize Machine_X64, source paths or individual fixture
symbols. Preserve zero values only when actually returned by the queried leaf.
The architectural query failure is not repaired by inventing public intrinsics or
returning UNKNOWN/empty features from the stdlib.

Further audit flags, not executed claims: own mnemonic parsing maps rdseed and
rdrand to the same Op::Rdrand, and current asm documentation describes synthetic
timestamp processor-ID and CPU-feature results. Their hardware prerequisites and
failure/status behavior need general compiler review before Machine_X64 exports
are counted complete. Native instruction emulation for ordinary arithmetic does
not establish truthful host/target CPU discovery.

The pending Jai reproducer passes source-built formatter/check/strict lint in
the current301-file owned scope, but its x64 execution **fails**. It is not included
as a passing functionality test or used to relax any API assertion.
