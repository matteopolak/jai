# Compile-time host file and process effects

## What it is

`jai-vm::host_effects` defines an explicit file/process protocol. `jai-driver::host_io::HostIo` implements an opt-in provider for driver-owned roots and individually reviewed, independently installed read-only commands. An empty provider and `NoHostEffects` deny all host work.

This is a tested provider boundary with checked stdio source bindings and VM dispatch. Ordinary `File.read_entire_file` and `File.write_entire_file` also depend on the actual allocator source chain; unchanged reference wrapper acceptance is tested separately. Ordinary `Process.run_command` needs resumable source continuations in addition to the virtual descriptor protocol. No function name grants a capability, no ordinary library wrapper is replaced by a fake intrinsic, and existing unsupported foreign calls remain unsupported.

The required self-authored stdio source fixture passes through the actual compiler and VM with an explicit temporary-root grant. The unchanged reference File fixture currently stops at the graph's callable overload alias handling for `Basic/Print.jai`; it has not established ordinary wrapper read/write acceptance. Provider and ABI proof tests remain separate evidence from full source-library or project support.

## How it works

A `HostPath` contains an opaque root capability and a relative path; it rejects absolute paths, parent traversal and NUL bytes. The provider resolves paths beneath a registered canonical root and rejects symlink components and nonregular input files. Read-only roots reject writes. Roots must be controlled by the driver without concurrent filesystem mutation: portable standard-library path checks do not provide an OS sandbox or eliminate races against hostile concurrent writers.

Transactions are keyed by the exact `SourceOrigin`, including its body and specialization bytes. Reads become bounded observations. `ReadFileForOpen` distinguishes typed OS failures such as a missing file from rejected authority, allowing the ordinary stdio adapter to return a null file and false result without poisoning a successful fallback transaction. This observation replays exactly like successful bytes; unknown roots, symlinks and exceeded budgets still reject the transaction. Writes remain in a transaction overlay, so subsequent reads see them without publishing a file. A failed evaluation discards the overlay. A sealed suspended evaluation retains it privately until resume or cancellation. Successful evaluation publishes one distinct output file with a same-directory temporary file and atomic rename; repeated writes to that same target publish the final bytes. Multiple distinct output files are explicitly rejected before publication because atomic publication of several unrelated filesystem paths is not implemented.

`ProgramId` identifies a driver registration of one canonical executable, one exact `ProcessArguments` vector and one working root. Argument boundaries remain separate OS arguments; there is no shell string, PATH search or inherited environment. A process request returns `Pending(HostRequestKey)` without starting a child. The scheduler must close the VM transaction before calling `service(key)`. Service captures stdout/stderr as bytes, preserves nonzero exit codes, enforces an output cap and deadline, and kills/reaps the direct child on timeout. The next source retry receives the cached result. Neither another service call nor replay of a committed directive starts the process again.

Registration is a trusted Rust driver operation, not authorization supplied by source text or an approval UI. Register only inspected installed commands that read data, avoid networks and external writes, and do not create descendants. Killing a direct child is not process-tree containment; this implementation is unsuitable for arbitrary subprocesses. Supplied compiler binaries, native libraries, linkers and objects must never be registered, executed or loaded on the developer host. Upstream custom linker, packaging and destructive process commands are not enabled by this provider.

The trusted embedding marks canonical original input files/trees with `protect_original_inputs` before any source observations. A writable ancestor root cannot overwrite those inputs, and reviewed executable registration rejects every path inside them. `protect_original_native_fingerprint` additionally records SHA-256 digests from the trusted native-input inventory: identical copies outside the protected paths cannot become reviewed executables. Both protections must precede source observations and reject overlap with existing program registrations. Granted static binary reads and source assets remain available; this protection does not filter filenames or extensions. The configured roots and native fingerprints come from trusted inventory, such as `corpus/reference-inputs.json` and `corpus/native-dependencies.json`, rather than source-provided fields. Reviewed installation or independently rebuilt artifact provenance is still required.

`ReviewedPrograms` resolves a decoded source exec request only when executable spelling, `argv[0]`, every remaining OS argument and canonical working directory match a registered grant. Unknown spellings do not trigger PATH search. Duplicate selectors are rejected as ambiguous, even if they point to the same program. `HostIo::reviewed_program_grant` creates a grant from the actual registration; Unix `register_read_only_program_with_argument_zero` includes reviewed native `argv[0]` behavior explicitly. Ordinary registration uses the canonical executable path as native `argv[0]`. This policy helper performs no OS calls and does not itself bind or execute source `execvp`.

`cancel(key)` rejects pending work without starting a program. `retire(origin)` releases cached observations after the scheduler retires that exact source identity; active or pending identities cannot be retired. Changes in a retry's request sequence reject the transaction, and a committed replay must consume exactly its recorded requests. Cached errors remain errors rather than causing another execution.

`FileCompilerSession` shares the compiler transaction with host I/O. Commit first finishes a cloned compiler session with the same logical workspace identities, validates host observations and publishes the single file, then replaces the compiler state with that finished shadow. Compiler rejection rolls back the host transaction before any rename; host rejection rolls back the original compiler state. Source wrappers receive `FilePathScope` from this session, so source path strings cannot select a root capability.

`HostIo::completion` polls the original readiness ticket using its full source identity. `FileCompilerSession::poll_host_request` forwards it only for the matching selected active or parked transaction. Servicing or cancelling a ticket preserves its cached observation until that source is retired. A resumed continuation can consume this observation without issuing a second `RunProgram` request or advancing the source request cursor. Polling does not start a process; another source identity and retired tickets are rejected.

`suspend_transaction` transfers the unpublished cursor and overlay to a sealed, noncloneable `SuspendedHostTransaction`. Provider identity and weak token lifetime prevent another provider, a new transaction for the same source, or retirement while the ticket is live. Other source transactions can proceed. `service_suspended` checks that both the process readiness ticket and host journal belong to the same source; ordinary `service` rejects a parked source. Resuming consumes the journal without replaying requests. Dropping the token discards staging; explicit `cancel_suspended` additionally rejects all its pending programs before releasing the token. Observations still require normal source retirement.

`FileCompilerSession` implements the VM `suspend`/`resume` hooks by parking matching compiler and host journals under the full source identity. A wrong identity cannot select a parked transaction. Cancellation drops staging directly, without attempting a resume that could fail after another compiler job has committed. VM continuation state and branch isolation belong to the scheduler; these provider hooks do not manufacture source `fork` results.

The source suspension loop calls `service_pending` after parking. `FileCompilerSession` validates every host dependency against the selected parked origin before servicing any of them, then launches each still-pending reviewed invocation once. Duplicate tickets and already completed observations do not issue another request or advance the journal cursor. A cached response or boundary rejection makes the pending VM leaf runnable; servicing preserves compiler staging and does not publish files. Other dependency kinds remain the compiler scheduler's responsibility.

A real OS `spawn` failure is a ready `ProcessLaunchFailed` observation carrying the actual positive raw error code and host platform. It does not indicate successful execution. Only a checked source adapter for the same platform may write that code into its virtual errno cell and resume the failed `execvp` call. Unsupported platforms or errors without an OS code remain boundary failures. Capability denial, argument mismatch, cancellation and budgets remain rejected effects; they are never disguised as a recoverable source launch error. Launch failure observations are cached just like completed output, so fixing the external condition during a retry cannot cause a previously failed invocation to start unexpectedly.

## How to change it

Extend the typed request/response model in `crates/jai-vm/src/host_effects.rs` and its driver implementation in `crates/jai-driver/src/host_io.rs`. Preserve capability membership, exact request replay and process readiness outside VM evaluation. New source bindings must validate declaration/module identity and the full foreign ABI, copy bytes through VM-owned memory, and respect VM budgets. Mapping ordinary source function names directly to host powers would bypass the source implementation and is prohibited.

The self-authored tests cover overlay reads, rollback, commit replay, read-only/default denial, capability mismatch, traversal/symlink rejection, byte limits, pending process lifecycle, literal argument boundaries, output limits, nonzero exits, cancellation and timeout cleanup. Process fixtures use fixed `/usr/bin/printf`, `/usr/bin/false` and `/bin/sleep` commands; they do not evaluate upstream `#run` scripts or use supplied binaries. Run them with `cargo test --offline -j 1 -p jai-driver host_io`. Successful provider tests do not establish full Focus or Jails project support.

The required `cargo test --offline --locked -j1 -p jai-driver --test process_abi` source fixture passes: its real `#run` body calls checked virtual POSIX pipe/write/read/close declarations, verifies partial reads, EOF and nominal `EBADF`, and produces 131. The required authored stdio source fixture also passes with the original-input deny policy installed before temporary file grants. These are source-route proofs; unchanged File and Process library compatibility has separate graph and continuation acceptance requirements described in [virtual stdio](virtual-stdio.md) and [the process adapter](process-source-adapter.md).

## Configuration

Trusted driver integrations populate [the original-input policy](original-input-policy.md) before registering roots or starting source evaluation. Its authenticated inventory retains original native fingerprints and protected trees even when a checkout is absent. The policy denies writes and copied-original execution; it grants no host capability.

`HostLimits` defaults to 16 MiB for cached payload bytes, 1,024 retained observations and registered capabilities, 1 MiB for combined process output, and a five-second process deadline. Roots and programs are registered explicitly through Rust API calls; there are no environment variables, CLI flags or implicit capabilities. Program arguments are checked against the byte limit before registration. The cached payload cap includes stored source identity bytes, request paths/arguments, file writes and response output; it is a data budget rather than a bound on total allocator overhead or transient copies. Registered root paths, executable paths and arguments have a separate aggregate cap of the same size. Source identity bytes are shared across observations rather than copied for every pending ticket.

Registration fingerprints the reviewed executable with RustCrypto SHA-256. Service hashes the same regular file again and rejects changed bytes or a replaced symlink before spawning. Fingerprint reads stream through an 8 KiB buffer and cannot exceed `HostLimits.bytes`; the fingerprint does not grant provenance or authorize copied original binaries. Registered paths and executable bytes must remain stable without concurrent external mutation: hashing followed by a portable path-based spawn cannot eliminate a hostile replacement race. Review and installation provenance belong to the embedding driver. The provider does not infer trust from a filename, execute lookup candidates, or load any dynamic library.

`ProgramScopeLimits` independently bounds a decoded exec capability table: 128 entries, 1 MiB of selector/argument bytes and 4,096 arguments by default. Source filename and `argv[0]` are separate identities because native programs can change behavior based on `argv[0]`.

## Dependencies

The VM protocol uses Rust's standard library and `SourceOrigin`. The driver provider depends on `jai-vm`, standard filesystem/process APIs, RustCrypto `sha2 ^0.11` and explicitly selected installed OS programs. The maintained crate supplies the [incremental SHA-256 API](https://docs.rs/sha2/0.11.0/sha2/); no handwritten cryptography or hashing subprocess is used. Cargo enforces a 14-day minimum publication age for registry resolution, and `tools/check_dependency_age.py` validates every locked dependency including transitive packages and yank status. The provider does not use LLVM, the original compiler, reference native libraries or shell interpreters.
