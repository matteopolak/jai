# Ordered record initialization

## What it is

The checked `OrderedRecord` expression constructs overlapping records with explicit zeroed or uninitialized backing. Its VM and native consumers retain original ordered field writes; source action producers and ordered constant recipes have separate publication boundaries.

## How it works

Backing initialization and field writes are separate facts. `ValueExpr::OrderedRecord` retains `OrderedRecordBacking::Zeroed` or `Uninitialized` followed by `Vec<(Box<[FieldId]>, ValueExpr)>` writes. Ordinary disjoint `RecordBuild` keeps its existing complete zero-backed contract.

Every placed constructor needs an ordered recipe, including complete ones. For defaults `a = 1`, overlaid `b = 2`, and an explicit override `a = 42`, the writes must occur in that order. A final-value map would store `a = 42` before `b = 2` and produce the wrong result. Keep declaration defaults and selected construction overrides as distinct entries in the original record member order, then append literal-site overrides in their written order.

Retain the exact selected member sequence when a record is materialized. Source spans are diagnostic locations, not ordering keys: quoted and inserted members may have origins elsewhere. The existing per-field readiness cache retains a final value after overrides, so it cannot supply an ordered journal by itself. Preparation needs separate completed action receipts for the original default and each override, published transactionally without evaluating a completed initializer again. A private receipt ledger now preserves the original capture, distinct action positions and canonical paths; a pending action keeps its original continuation ticket, and a repeated request for a completed action returns its retained receipt. Publishing an invalid value leaves earlier receipts intact.

A write retains a nonempty path of actual canonical `FieldId` values and a checked terminal value. Each path step validates its owner and resulting type. Selected-target field offsets are added with checked arithmetic. The terminal extent is written directly; the operation never reads a skipped parent field to manufacture a complete replacement. For `base: Base = ---; base.value = 42;`, sibling bytes remain uninitialized.

`---` contributes no write. It is neither a zero value nor an undefined store. Complete placed recipes can start zeroed; recipes with genuine skipped defaults use uninitialized backing and write only the selected defaults and overrides. Initializers evaluate once and store before the next initializer evaluates. Repeated paths are legal because later overrides must retain their ordering and effects.

Validate every path, terminal type, extent, and work bound before evaluating the first initializer. Native preparation performs that full preflight before allocating and emitting ordered stores. The VM builder's image limit is only one admission check; its caller must also charge cumulative retained values, image/patch metadata, and evaluation work.

VM construction in `execute/ordered_records.rs` retains an exact byte image, initialized mask, and pointer provenance. It prepares every actual path owner and selected-target extent before allocating backing or evaluating an initializer. Ordinary evaluation reserves the backing against the actual memory quota while evaluating each initializer. The resumable plan and machine keep that image and the next write index across pending work and detached continuation transfer without replaying completed effects. The retained state charge includes the image, initialization mask, metadata, and prepared write entries; patch encoding has a separate transient admission bound. Native construction uses the selected-target physical extent and semantic byte offsets. Whole copies must retain the complete image, including known padding bytes.

Constant recipes must retain the same backing policy and write paths rather than collapse into `ConstantKind::Record`. Runtime snapshot publication remains fail-closed when initialization holes or pointer metadata cannot be represented by a checked receipt. Native constants must preserve actual relocations; partially overwriting a relocation requires an explicit representability rule. By-value foreign calls with placed records need a separate ABI proof or explicit rejection: overlapping aliases cannot automatically be treated as independent aggregate members.

The memory-owned `finish_ordered_record` normalizes pointer and code receipts through the owning memory domain before exposing a finished VM image. Independently encoded pointer patches may otherwise contain equal local token bits despite referring to distinct objects. Receipt normalization must retain the original initialized mask and aliases, with its transient work and retention charged before publication.

## How to change it

The expression is registered with verifier, disposal, traversal, VM ordinary/resumable execution, and native construction. Extend the ordered constant form with its constant verifier, retention, identity keys, and static-data consumers in one coordinated change. Keep [placement layout](record-placement-layout.md) identity checks and [storage-only snapshot](aggregate-storage-snapshots.md) initialization checks independent of expression evaluation.

Before accepting constructors, verify complete overlap defaults followed by an override, repeated writes with observable effects, a nested write through an uninitialized parent, unknown scalar read rejection, pointer provenance after whole copies, and pending execution without replay. Run the [Thread placement fixtures](thread-placement-acceptance.md) through the VM and freshly emitted native O0/O2 programs. Staged helper tests do not establish source constructor support.

Six private receipt tests pass for ordered `1, 2, 42` actions, pending continuation identity, terminal NoWrite, malformed-value rollback, foreign-ticket rejection and source-order admission. Six isolated builder tests also pass against a copied current VM crate compiled with warnings treated as errors. They exercise complete overlapping defaults and a later override, nested writes without parent reads, initialized-mask retention, owner-check rollback, retained-image accounting, and repeated real data-pointer writes followed by an actual memory whole-copy. The production memory-owned rvalue finalizer and ordinary/resumable ordered expression consumer are now implemented. ## Configuration

There are no new environment variables or CLI switches. `OrderedRecord` is deliberately classified as non-static until an actual typed, relocation-aware constant recipe consumer is available. Physical aliases and nested partial writes also cannot be represented by the independent semantic-field callback contract; that callback proof remains absent instead of reconstructing a final field map. The selected layout policy, VM value-cell and evaluation-depth limits, and native target data govern storage and admission. Compound placement anchors and indexed or dereferenced default-override paths remain separately unsupported. Skipped override values in record bodies or literals also retain an explicit boundary: declaration-site `field: Type = ---` is established, while suppression of an earlier default by an override `field = ---` still needs source evidence.

## Dependencies

The contract depends on `jai-types` owner-bound field identities and layout, source record/default metadata in `jai-sema`, checked expressions and constants in `jai-ir`, VM byte images and storage snapshots, and LLVM record memory helpers. No supplied native compiler, library, object, or executable is loaded or run.
