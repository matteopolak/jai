# Preserve real Windows dynamic SDK providers

Job 117243082265 reported static `.lib` archives without supported DLL import providers for FreeType, lz4, meshoptimizer, MojoShader, mbedTLS and stb_image_write. The compiler's strict diagnosis is retained. Inspection found that the normal native builder already links real DLLs, but writes their matching `/IMPLIB` output inside a temporary directory that is then deleted.

The builder now retains those linker-generated import archives in `dynamic-imports/<name>.lib`, alongside the unchanged static `<name>.lib` and real `<name>.dll`. The complete package inventory requires all three; a static-only old cache is incomplete and rebuilds. Prebuilt providers, SDL3's separate builder and MinGW static cross packages retain their existing contracts. No archive is renamed to masquerade as a DLL or synthesized from guessed exports. Export definitions still distinguish functions/data from actual compiled symbols.

The Windows catalogue wrapper puts an existing `dynamic-imports` directory before its corresponding SDK directory. The original compiler import parser/provider mapping and strict failures are unchanged. Native executables receive real SDK DLLs app-locally, with basename/content collision checks before any copy. Caller-owned Mesa is preserved: a conflicting DLL causes a test failure rather than overwriting it. This allows native linking against those real import libraries; static package consumers still have their original archives.

Validation: five package/supervisor tests pass, after the initial controls reproduced discarded import output, missing inventory and absent deployment behavior. Twelve existing runtime/coverage tests pass. Scoped Ruff and Windows workflow actionlint pass; the new test is wired into all three normal Windows native consumers and both workflow path selection layers. These are configuration/mocked-linker/byte-identity controls on Mac, not Windows DLL execution or ABI proof. Normal Windows x64/ARM64 CI must build and load the actual packages.

Remaining closure: `Crt`, `ffi`/`binding_ffi` and Clang SDK providers need their proper reviewed provider/build mappings; this patch does not invent aliases or claim those failures fixed. Actual Windows replay remains red until checked. The main loader, GPR/XGETBV/output work and all original assertions remain intact.

Tradeoff: each native test executable receives the available SDK DLL set rather than a minimal per-executable dependency graph. This adds hash/read/copy cost and disk usage. A future deployment planner can inspect the actual PE imports and recursively stage only required matching providers; it must retain full dependency/identity validation and cannot guess missing providers. The current implementation favors a complete, explicit package closure and rejects conflicts.
