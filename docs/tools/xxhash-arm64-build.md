# Pinned xxhash070 Windows ARM64 build repair

The candidate 2fa2bc2 Windows ARM64 failure is a real target-selection defect in
xxHash v0.7.0, not a missing dependency that should be replaced by a shim.
`xxh3.h` selects `__emulu` whenever `_MSC_VER` is defined. Clang defines that
macro for ARM64 Windows, but Microsoft documents
[__emulu](https://learn.microsoft.com/en-us/cpp/intrinsics/emul-emulu)
only for x86/x64. The pinned source already contains equivalent portable
unsigned 32-by-32 to 64-bit multiplication in the alternative branch.

## Scoped production correction

Only `tools/build_native_libs.py`'s xxhash070/windows-arm64 compile path changes.
The new helper rechecks every pinned file's SHA-256, requires revision v0.7.0
and exactly one recognized intrinsic guard, then writes an isolated build copy.
The one-line patch is:

```diff
-#ifdef _MSC_VER
+#if defined(_MSC_VER) && (defined(_M_IX86) || defined(_M_X64))
 #   include <intrin.h>
     /* MSVC doesn't do a good job with the mull detection. */
 #   define XXH_mult32to64 __emulu
```

ARM64 consequently selects upstream's existing masked unsigned multiplication.
The masks preserve the intrinsic's unsigned 32-bit operand truncation. No hash
algorithm, state layout, exported API, assertion, compiler target, CRT flag or
link flag is changed. The canonical downloaded sources stay untouched. Other
platforms compile their original source paths and flags, including MinGW ARM64
which already uses the GNU path. The integrator's rpmalloc artifact logic and
all compiler/stdlib/Extensions sources are outside this change.

This is an explicit pinned-source build patch, not an upstream release update.
Its maintenance cost is a staged copy of four small source/license files for
this target. Unexpected source/hash/anchor changes fail before compilation;
future version updates require review of the patch and the version-dependent
XXH3 hashes/state ABI. There is no fabricated __emulu implementation. Performance
is not benchmarked; ARM64 object inspection shows native multiplication, with
no external intrinsic call. A future compatible upstream pin can retire the
patch after ABI/hash review rather than silently changing library behavior.

## Reproduction and evidence

Host: macOS ARM64, Homebrew Clang/LLD 23.1.2. Set INCLUDE to the downloaded
Microsoft CRT include, SDK ucrt/shared (and um for the CLI test) directories.
Set LIB to the official ARM64 desktop CRT, oldnames, SDK ucrt and SDK um
directories. Clang honors these SDK search paths on this cross host.

The original source compiles using the production static-CRT/omit-default-lib
flags and the real Clang intrinsic header. `llvm-nm --undefined-only` reports
`__emulu`, free, malloc and memcpy. Linking with `--target=aarch64-pc-windows-msvc
-fms-runtime-lib=static -shared`, the generated .def and `/DEFAULTLIB:libcmt`
fails specifically with undefined __emulu. The patched production compile
helper removes that undefined reference and links successfully against the
same SDK/runtime. The only cross-host driver addition is `-fuse-ld=lld` to
select the installed linker; there is no /NOENTRY, unresolved-symbol allowance,
CRT substitute, custom header declaration or diagnostic suppression added.
Using the Microsoft intrinsic header ahead of Clang's instead diagnoses the
original undeclared ARM64 intrinsic earlier; the same source guard fixes both
include orders.

Actual evidence retained locally under `target/xxhash-repair/`:

- `unit-red.log`: three expected policy failures before the repair;
  five current offline policy tests pass afterwards.
- `link-red.log`: the confirmed undefined __emulu link failure.
- `link-green.log`, `arm64-dll.log`, `green/`: linked ARM64 DLL, archive and
  object. DLL machine is IMAGE_FILE_MACHINE_ARM64 (0xAA64). Its exact 24 export
  definitions equal the original object's export definitions. No __emulu shim
  is defined or imported.
- `vector-cross-link.log`: official sanity-check executables cross-link against
  the static archive and actual DLL import library. Both PE machines are ARM64.
- `host-vectors.log`: official static and shared sanity checks execute and pass
  on macOS ARM64. The new verifier repeats these real host executions.
- `x64-preservation/`: original Windows x64 source compiles against real SDK
  headers, retains all 24 exports and has no unresolved __emulu.

Offline policy tests use tiny original inputs and mocked compiler dispatch to
test hash/anchor rejection and target selection; they are not native evidence.
No Linux execution or Windows x64 native/DLL runtime pass is claimed here.

## Required native Windows gate

From a matching Windows developer SDK/toolchain environment, run:

```sh
python tools/check_xxhash_native_build.py --platform windows-arm64
python tools/check_xxhash_native_build.py --platform windows-x64
```

Each invocation uses the actual production builder with a worktree-local,
hash-verified source cache. It checks the DLL machine and exact 24 exports,
builds an import library from those exports, and runs the official sanity tests
in two native executables, linked statically and dynamically. Outputs are saved
before checking failure status; failures are not whitelisted. `llvm-dlltool`,
`llvm-readobj`, `llvm-nm`, `llvm-lib`, Clang and the matching Windows SDK/CRT must
be available. Explicit ARM64 selection matters when Python itself runs as x64.
Coordinators should also retain their normal Jai binding/application checks.

Local checks:

```sh
python3 -m unittest discover -s tools -p test_xxhash_native_build.py
python3 tools/check_xxhash_native_build.py --platform macos-arm64
ruff check tools/build_native_libs.py tools/check_xxhash_native_build.py tools/test_xxhash_native_build.py
ruff format --check tools/check_xxhash_native_build.py tools/test_xxhash_native_build.py
```

The ARM64 COFF, full CRT DLL link, export equality and executable link results
are genuine cross-tool evidence. They do not prove Windows DLL loading, native
hash execution or the full candidate matrix. Those gates remain pending native
CI. No CI, push, release action or publishing was performed.
