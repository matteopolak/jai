# Modules, workspaces and practical example patterns

This page records module/import structure and the larger kinds of programs shown in the supplied examples/corpus. It focuses on language-level integration patterns and flags when behavior belongs to build tooling rather than the language core.

## Source evidence

The tutorial corpus covers imports and loading, `using`, scope levels, module parameters, workspaces, command-line input to metaprograms, generated build strings, custom checks and hooks, and cross-compilation. The examples include alternate imports, generated declarations, shared libraries, iOS and wasm outputs, VR and graphics, games, animation, visualization, file conversion, mail generation, and system inspection.

## Imports and modules

`#import "Name";` introduces a module. The lessons show imports by module name and file, local files and subdirectories, and names made visible through module members. `using` can expose selected members in the current scope; it can also be applied to aggregate members. This is a name-resolution feature, not code copying. `using,only(names) Alias :: #import ...;` and `using,except(names) Alias :: #import ...;` bind the module under `Alias` and also bring the selected exports into the containing scope; the alias remains usable for qualified lookup. `only` admits the listed names, while `except` admits exports other than the listed names. The tutorial also demonstrates computed name lists, and says filter names need not exist in the imported module. File/global-scope examples show declarations shared across files in a module context.

The advanced `using,map(mapper)` form is demonstrated on struct members. At compile time, the mapper receives the aggregate member names and can rewrite a name, replace it with the empty string to omit that member, or leave it unchanged. Assignments through mapped member names update the original aggregate member. The example mutates the supplied name slice and requires any replacement strings to remain valid after the mapper returns; it does not mutate the compiler-owned string contents. These guarantees apply to the demonstrated aggregate-member form. The guide does not establish mapped names for module imports or reexports, nor mapping behavior for overloaded operators. `only` and `except` preserve original names. The module-import examples do not demonstrate renaming imported exports. The examples do not show whether `Exported :: Impl.mutable_global` is rejected or captures an immutable value, and they do not authorize it as a live mutable-storage alias. Use the documented `using` import/re-export form to expose the original declaration. A `type_of` query on a foreign variable establishes only its type; it does not establish mutable aliasing or a storage re-export.

The lessons distinguish `#import` from `#load`: an import compiles a separate module with its own module scope and can be brought in anonymously or under a namespace; `#load` adds another file scope under the application/module scope. `#import,file`, `#import,dir`, and `#import,string` demonstrate explicit source selection and generated source. Named `#import` aliases and `using` declarations follow the active scope directive. Reviewed independent official controls additionally establish that a plain top-level anonymous `#import` after `#scope_file` contributes to the containing module import environment, so a loading file can use its names; this does not make named aliases or ordinary file-private constants public. Conditional/generated/body import placement is not established by that control (see `docs/specs/questions/loaded-import-scope.md`). Each loaded file instead starts in its own file scope, with `#scope_export` active by default; the caller's active directive does not carry across `#load`. Within a file, `#scope_file` selects the file-local scope and `#scope_export` selects the containing application scope or a module's importer-visible export scope. A file-local declaration can shadow a same-named enclosing declaration. Lookup proceeds from the current file scope to its enclosing application/module scope and then to preload; an imported module cannot look into the importing application's scope. `using value;` exposes aggregate or enum members in the current scope, and `using name: Type;` combines declaration and exposure. Scope shadowing can make short names ambiguous, so resolution follows scope nesting, not file load order.

The examples directly support standalone aggregate `using,only(...)` and `using,except(...)` as well as computed name lists: they select which original member names are exposed, and a filter may name a member that does not exist. Module-import `using,only(...)` and `using,except(...)` select importer-visible exports while leaving the named module alias available for qualified access. A bare `using Alias :: #import ...` can be deduplicated, while repeated filtered imports are explicitly not deduplicated and can conflict. The corpus does not establish how separate filtered imports merge overloaded procedures, how conflicting non-procedure exports are resolved, or whether aggregate filters compose with `map`; those cases need separate compatibility evidence.

Module parameters are demonstrated as compile-time inputs to a module, including local module instances configured by caller-provided values. The lesson states that imports with identical parameter argument lists deduplicate; different lists create separate module instances, even if defaults would make effective values equal or named arguments have equivalent values in a different order. The author describes this as a fussy rule that may change. Import replacement examples show build configuration selecting alternate source for a dependency. Those are distinct mechanisms: module parameters configure a module instance, while replacement changes which implementation is loaded.

The source lessons refer to `Runtime_Support` for built-in runtime facilities and context members, but do not demonstrate an explicit parameterized import of that module. They therefore do not determine whether an explicit import shares the implicit runtime module instance or creates a distinct instance when arguments differ. Treat any reserved-module exception as compiler-compatibility behavior rather than a general Jai module identity rule until directly demonstrated.

The source lessons do not establish all path search rules, import-cycle behavior, overload merging across multiple export sources, or replacement precedence. The parser/sema implementation should obtain those rules from dedicated compiler evidence rather than assuming host filesystem conventions.

Scope directives make declaration placement explicit: `#scope_file` places following declarations in the current file scope, while `#scope_module` and `#scope_export` place them in the containing module scope. Both module-scope forms make names available across that module's files, but only `#scope_export` adds the names to the module's importer-visible export list. A named import can therefore exist while its private module-scope declarations remain unavailable to importers. In an application that cannot itself be imported, the tutorial notes that this distinction has no practical importer effect. Generated module files can use `#placeholder NAME;` as a substitution point filled by the build/metaprogram that emits or loads the source. These directives affect declaration visibility and generated-source integration; they are not ordinary runtime statements. `#program_export` marks procedures or data intended for an exported program/library interface in the examples, while actual symbol export and ABI behavior remain dependent on the selected output target and platform.

## Build and workspace model

The how-to material treats a workspace as a compilation unit with build options, target OS/CPU, output mode, and a metaprogram context. A custom metaprogram can add files/build strings, create another workspace, alter its options, intercept compiler messages, and wait for completion. Cross-compilation examples distinguish host from target and use object-file output where target libraries/linkers are unavailable.

`#run` and `#modify` can make compile-time host/target boundaries observable. A metaprogram may provide build strings explicitly when compile-time file operations would otherwise execute against the wrong platform. This is build-system behavior and should not be conflated with runtime `#if` selection.

## What the example projects demonstrate

The examples show the language applied to practical systems: command-line tools, file processing, a hash table test, a treemap viewer, games, skeletal animation, graphics APIs, a DLL boundary, iOS/wasm outputs, generated code, and a small mailer utility. Together they provide evidence that the syntax supports larger modules, manual memory management, callbacks/foreign interfaces, generated declarations, and ordinary application control flow.

The corpus also embeds non-Jai source using `#string` delimiter forms (including end-delimited blocks) and obtains source location/path values through `#file`, `#filepath`, and `#location`. These are compile-time source/build inputs; paths should not be assumed to be runtime working-directory paths. `#compile_time` is used as a compile-time context query in conditional logic. The examples use these facilities for generated shaders, build text, diagnostics, and source-relative assets; encoding and escaping rules beyond the demonstrated delimiter forms remain an edge for targeted evidence.

The command-line lesson treats arguments after a separator as metaprogram input, so command-line parsing is a build/metaprogram concern rather than a language expression feature. Build examples also set output kind and target properties; target-specific libraries and linkers remain external build dependencies.

The examples can reveal idioms and interactions, but application code is not a normative definition of every edge case. A library's local convention (for example, ownership or error handling) should not be generalized into a language guarantee.

## Guidance for implementing `jaic`

- Keep module loading/name lookup separate from expression parsing and typechecking; import and file scopes participate in declaration collection.
- Preserve the distinction among file scope, module scope, caller scope for inserted code, and workspace-level metaprogram state.
- Represent compile target and host compile-time execution separately.
- Treat import replacement and module parameters as independent inputs to module resolution/instantiation.
- Use small how-to programs for direct syntax claims and larger examples as interaction evidence.
- Maintain an explicit unresolved list for search paths, cycles, visibility, replacement precedence, and module cache identity until corroborated by allowed source evidence or compatibility tests.
