# Staged corpus acceptance

## What it is

`tools/check_corpus.py` inventories every pinned reference and recent upstream Jai source and attempts explicitly selected roots with this repository's Rust compiler. Lexical acceptance never counts as compilation; ordinary module checks, program builds, deliberately rejected programs and runtime evidence are separate results.

## How it works

Build our CLI with `cargo build -p jai-cli --locked`, then run:

```sh
python3 tools/check_corpus.py --report artifacts/corpus-acceptance.json
python3 tools/check_corpus.py --all --through parse --report artifacts/corpus-parse-current.json
python3 tools/classify_corpus_failures.py artifacts/corpus-parse-current.json
python3 tools/check_corpus.py --all --through check
python3 tools/check_corpus.py --select 'reference:how_to/001_first.jai' --through codegen
python3 -m unittest discover -s tools -p 'test*corpus*.py'
```

The default manifest selects reference tutorials, a standard module, metaprogram roots and roots from all seven pinned upstream projects. `--all` attempts every inventoried source, including support files; it is a diagnostic sweep, not proof that each file is an independent project. The driver resolves recursive loads and unparameterized imports with independent module/file visibility. Parameterized and conditional dependencies remain unsupported. No synthetic replacement source or import stubs are supplied.

Each report retains all 2,142 source rows, even when a smaller selection is attempted. Unselected rows are `not-run`, missing or modified selected sources are `blocked`, unsupported syntax is `failed`. Stages stop after a failure. Manifest entries with `kind: module` and unclassified inventory support files use `check-library`, which checks all reachable bodies without an application entrypoint. Support-file checks validate bodies without claiming a standalone application. Manifest program/negative/metaprogram cases use application checking and require an application-owned `main`; LLVM output, linking and project builds have separate requirements. `jai-rs parse SOURCE` decodes source with the shared decoder and calls the file parser with a source registry and shared symbol interner. It validates syntax and records imports, loads and visibility directives without resolving dependencies, reading loaded files or executing metaprograms. A parse pass is syntax evidence only. Graph-aware semantic resolution powers `check`, `check-library`, `emit-llvm` and `build`; CLI semantic checking currently supplies `NoEffects` to the compile-time VM, so these check results do not establish metaprogram effects or native foreign execution; successful syntax parsing does not imply support for all declared types or compile-time behavior.

When the integrated CLI is temporarily blocked by an unfinished semantic migration, an isolated adapter may call the same source decoder, lexer and `parse_file` APIs. Pass `--frontend-adapter --compiler target/corpus-frontend-adapter/debug/jai-rs --through parse`; the harness rejects later stages and labels `compiler.evidence_kind` as `isolated-frontend-adapter`. Adapter source/manifest/lock hashes are retained alongside compiler fingerprints. Such results establish frontend syntax evidence only and must never be presented as successful integrated CLI checking or native compilation. The adapter lives under ignored local `artifacts/frontend-adapter/`; it is diagnostic tooling, not a replacement compiler product.

`tools/classify_corpus_failures.py` groups measured first-stage failures (`--stage lex|parse|check`, default `parse`) by exact diagnostic and records SHA-256-verified source locations, sorted with modern upstream sources first. It annotates the failing line with lexical feature hints from the existing inventory scanner; those hints are observations, not proof of the failure cause. Changed source locations are rejected instead of being attached to stale diagnostics. Semantic diagnostics can point into a loaded dependency: the report distinguishes that verified diagnostic source from the selected root. Multiple roots blocked by the same dependency count as multiple root failures, not independent implementations of the same failing feature. Each diagnostic group also aggregates exact dependency locations by affected-root count, distinguishing one widely imported module blocker from unrelated failures with similar messages. Root and dependency files must both match their recorded hashes. Its local JSON output retains no source excerpts, and later failures hidden by the first error are not counted. Regenerate this report after rebuilding our compiler; an older parse report is not current coverage.

Negative cases specify a diagnostic substring per stage. Only exit code 1 with that substring is `expected-rejection`; an unrelated unsupported construct, crash, timeout or incorrect successful acceptance fails the case. The OpenJai false assertion now produces its intended diagnostic and counts as an expected rejection. The book's polymorphic mismatch still fails earlier in a dependency and does not count as a successful negative test.

Reports record exact commands, exit codes, bounded stderr, source and compiler binary SHA-256 values, input manifests and compiler-source fingerprints. Compiler stdout is not retained because lex/IR output can reproduce source material. Before each LLVM/native output stage, the harness removes only that stage’s exact generated leaf inside its owned temporary or repository-target scratch directory. It rejects source/compiler aliases, symlinks, corpus paths and mismatched scratch roots. A successful command that writes no new file fails; native build output must also be an executable regular file. Semantic stages never inherit output hashes from prior files. Successful fresh generated artifacts have their own SHA-256 hashes. Binary and current source fingerprints are recorded independently: this does not prove a stale binary was built from those exact sources. Outputs live in a temporary directory outside the corpus and are removed afterward. Reports remain local; this tool uploads nothing.

The harness executes only `target/.../jai-rs`. It never executes reference tools or upstream build scripts. This general harness does not execute generated programs. The separate [reviewed native example runner](native-corpus-examples.md) verifies narrowly approved original programs with exact runtime assertions. Host linking requires an explicit, reviewed `host_build_reviewed` manifest entry: review the source and transitive loads for pure generated IR, foreign declarations, native objects, metaprogram behavior, SDKs and target requirements first. The general root manifest has no approved native builds; the separate native example manifest records its own reviewed cases. Approved builds invoke our CLI with `/usr/bin/clang` as the backend, overriding inherited `JAI_RS_CLANG`; missing tooling is a blocker. Platform and graphics projects remain unverified until genuine dependencies and appropriate target SDKs exist.

The report intentionally has zero `project_build_successes`: per-root checking cannot establish upstream workspace builds and target correctness. Complete build evidence must earn those counts.

Acceptance buckets share an immutable integrated compiler but retain separate entrypoints and profiles: [standard libraries](standard-library-acceptance.md), [Focus and Jaison](focus-and-jaison-acceptance.md), [Vk-Engine and sgpu](graphics-project-acceptance.md), and [Jails and book entrypoints](newer-project-entrypoints.md). Their selected roots, dependency/runtime settings and stage totals must be read independently from the broad per-file sweep. Reviewed standalone native examples have a separate manifest and behavior assertions.

## How to change it

The manifest and report formats are documented by `corpus/acceptance.schema.json` and `corpus/acceptance-report.schema.json`. The harness checks critical manifest constraints without adding a JSON Schema runtime dependency. Add reviewed roots to `corpus/acceptance.json` using exact `repository:path` IDs from the pinned manifests. Keep metaprogram roots instead of substituting their eventual generated programs. Add dependency and target metadata, and explain any negative expectation. Update `evaluate` and its tests when introducing a separately observable stage or real workspace acceptance. For diagnostic grouping, change `tools/classify_corpus_failures.py`; lexical hint patterns belong in `tools/inventory_corpus_features.py`, and do not establish parser support. Do not infer successful stages from diagnostics or skip unsupported constructs to improve totals.

The first blockers are the remaining file-parser grammar, parameterized/conditional module dependencies, compile-time assertion diagnostics, aggregate semantics and compiler workspaces. Once those work, extend curated roots through LLVM output before approving native linking. A whole-corpus run is optional while those foundational blockers dominate.

## Configuration

`--compiler` selects a repository `target/.../jai-rs`; `--manifest` selects an acceptance JSON manifest; `--report` selects local output. `--through` is `lex`, `parse`, `check`, `codegen` or `build` (default `check`). `--select` repeats exact source IDs and overrides the default case selection; `--all` selects all pinned sources when no explicit selections exist. `--timeout` bounds each subprocess (default ten seconds). Read-only source roots cannot contain report output.

`--bootstrap off` (default) explicitly sets `JAI_RS_PRELOAD=off` and `JAI_RS_RUNTIME_SUPPORT=off`, unsetting ambient `JAI_RS_STDLIB`. This diagnostic checking profile does not establish standard-library bootstrap. `--bootstrap search` selects the actual reference module directory via `JAI_RS_STDLIB` and sets `JAI_RS_PRELOAD=search`.

`--bootstrap authored` checks unchanged corpus sources against the independently written `prelude/Preload.jai` and `stdlib/`. Project module directories retain their search precedence; the reference standard library is excluded from this profile. This makes API compatibility failures in the replacement library observable without rewriting upstream inputs. All three profiles disable Runtime_Support, so a body check does not establish runtime initialization or execution. Use the separate standard-library runtime profile and native behavior runners for those stages.

For example, `python3 tools/check_corpus.py --compiler target/corpus-snapshots/<sha>/jai-rs --bootstrap authored --through check --report artifacts/corpus-authored.json` attempts the curated roots with the replacement library. The report records the actual selected prelude and module paths with every compiler command, and fingerprints every authored library/prelude source in `input_manifests`. Source or compiler changes during the sweep invalidate its capture. Extend `Bootstrap` and `bootstrap_environment` together when adding a profile; preserve project precedence and avoid inherited ambient source selections.

The harness sets and records `JAI_RS_MODULE_PATH` per source: actual nearby `modules/` or `Modules/` directories up to the project root, then the selected standard-library directory. The authored profile excludes `reference/modules` even when an example's parent would otherwise rediscover it. Explicit relative `#load` directives and upstream-owned module directories retain their original meaning. It overrides inherited module paths, supplies no renamed substitute modules or generated stubs, and leaves absent dependencies as blockers. Native target flags exist in the CLI, but this harness does not select cross-target SDKs; manifest targets describe requirements rather than verified target configuration. The classifier accepts `--stage lex|parse|check` and `--output`; isolated adapters use `--frontend-adapter` and can establish only lex/parse evidence.

## Dependencies

Python 3.11+ standard library, our Rust CLI, `corpus/reference-inputs.json`, `corpus/upstreams.json`, read-only `reference/` and fetched `corpus/upstream/`. No new Python or Cargo dependency is needed. Approved native builds additionally need trusted `/usr/bin/clang`. SDKs, genuine native bindings and Compiler workspace APIs remain project-specific blockers. See [reference compatibility](reference-compatibility.md) and [upstream corpus](upstream-corpus.md).
